# Kani harnesses for paraxiom-pqc

A separate crate, outside the library's workspace, so that the library's sources and dependency
graph do not change. Run from this directory with `cargo kani` (Kani 0.67.0 was used); one
harness with `cargo kani --harness <name>`.

Each harness is a bounded model check of a small, stated property. The bounds (lengths, list
sizes, unwinding) are in each harness's comment. Nothing here covers the cryptographic
computations themselves, timing, or input beyond the stated bounds.

- `falcon_gate::falcon_gate_matches_target`: the constant `sign::FALCON_SIGNING_AVAILABLE`
  equals the documented target condition, for the target Kani compiles for. It checks a
  constant, not the cfg on the Falcon modules.
- `zeroize_clears_allocation::*`: after `zeroize()` on a `DecapsulationKey`, `SharedSecret` or
  `SigningKey` whose buffer has any contents, any length up to 4 and any spare capacity up to 2,
  every byte of the allocation is zero and the allocation is still the same one.
  `control_vec_clear_does_not_clear_bytes` is the control: it is expected to fail its check
  (`#[kani::should_panic]`), which shows the check can fail. These harnesses do not cover the
  drop itself: Kani does not route deallocation through a `#[global_allocator]`, so the
  "cleared when freed" check is done at run time by `tests/zeroize.rs` instead. The `Drop` impl
  that calls `zeroize()` is generated by `#[derive(ZeroizeOnDrop)]`.
- `length_checks::falcon_verify_refuses_a_short_key`: `falcon::verify`, and `sign::verify`
  under each Falcon label, refuse a public key of each length 0 to 32 bytes with any contents.
- `length_checks::policy_new_*` and `combine_refuses_*`: `Policy::new` accepts exactly
  non-empty lists without duplicates (up to 4 mechanisms, symbolic), and `Policy::combine`
  refuses secrets that do not match the policy (enumerated counts, mechanisms and lengths,
  symbolic bytes).

Not covered: harnesses for `kem::decapsulate`, ML-DSA signing and verification and SLH-DSA
verification on wrong-length input were tried and were not tractable (CBMC also explored the
cryptographic code that the length check rules out, and none finished). Those entry points are
covered by the property tests and the fuzz targets instead, which test and do not prove. See
the comment on `length_checks` in `src/lib.rs`.
